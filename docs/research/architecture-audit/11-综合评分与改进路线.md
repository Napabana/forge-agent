## 7. 最小实施顺序、成本与验收

1. **0 元 API 的离线验证**：先在完整 repo checkout 执行现有 51 条原型和 7 条新行为/归档测试，以及旧的 Completion、Runner、Eval、权限/Runtime 测试。任何现状刻画用例失败都需先修正结论。
2. **安全优先**：Provider Key 传播真值表 + 非真实密钥的子进程/Grader/MCP 测试；对不可信代码采用独立最小环境/沙箱。
3. **评测先行**：Stage09 H0 累积证据→生产 Trial schema/scoreable/failure domain/clean-up 的最小版本化接线；在同一 Forge SHA 上跑完整无 API 回归。
4. **停止/权限/成本**：正向 CompletionCandidate（仅提示收尾不伪报 success）+ TestEvidence provenance；确保 unattended 沙箱边界；Repo Map counter cap、Trial 级总预算。
5. **真实 A/B 最后**：固定模型、任务 SHA、依赖、工具与权限、Verifier/timeout、总预算、seed/repeats，每次只改一个模块并输出配对成本/成功率差。

工作量仅供排序：P0 Secret 约 2–5 人日验证/方案，P0 Eval 约 1–3 人日，Completion + TestEvidence 约 2–4 人日，RepoMap/成本 约 1–3 人日。不做总工期承诺；实际依 Forge 本地环境和回归结果而定。

## 8. 项目面试答法（能够拿出证据）

**Q：Agent 与 Harness 有什么区别？**  
Agent 是模型决策和调用工具的循环；Harness 是任务/执行权限/环境/Context/可验证收尾/Trace/独立评测等宿主控制层。本项目有完整执行环，但实际 Typer R1 提示需要更严格的正向停止协议与费用治理。

**Q：怎么证明 Agent 输出可靠？**  
不能仅以模型生成成功或 pytest 单一 PASS 作为真相；冻结任务合同、独立 Verifier/测试范围、代码快照与终态，按固定环境和样本重复统计任务功能结果/自然完成率/故障域。

**Q：为什么 Planning/Recovery 不一定有收益？**  
R2 联合变体两组都 23/24，但 Token 增 31.9%；单次联合消融不能归因到某个模块，应只在复杂任务/失败模式下条件启用并做独立比较。

**Q：怎么降低模型调用费用？**  
区分单请求 TokenBudget、Repo Map 是否过大、是否重复发送固定上下文、自然停止是否及时、Provider 重试/Timeout，分别用 Trace 量化并制定 Trial 级限额，不能用缩小 Context Window 冒充费用控制。

**Q：Docker 是否足够安全？**  
不够。Docker 负责 OS 隔离，工具 Permission 负责授权范围，Provider Key 的驻留/传播与 MCP Host 进程还需独立限制。当前只将它列为需要动态证明的 P0 准入问题，不冒称已经攻击成功。
