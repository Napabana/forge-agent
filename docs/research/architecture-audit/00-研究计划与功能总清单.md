## 0. 本次工作的目标与限制

目标是回答：Forge Agent 的全部设计是否合理，哪些架构取舍有可验证的优势/成本，能否构建可信的外部 Benchmark baseline，后续如何在**不混淆 Harness 变化与模型训练变化**的条件下开展 Teacher→Student→SFT→GRPO；并形成可用于实习面试的源码依据和解释。

原则：不因用户只点名 Repo Map、Skills、工具而忽略其他模块；按七份设计文档的体系建立全量功能树，补齐横跨各文档但容易遗漏的 LLM Provider、配置、API Store、AgentBus、错误与终止语义、Delivery、Trace、Experiment、Training Interface。研究期间原则上只改审计文档，不改功能代码或评测配置，不将未执行测试标为通过，不做收费模型调用。

## 2. 已核对的宏观执行链

```text
CLI run / Chat / HTTP API / GitHub Issue
          │
          ▼
ExecutionRunner（RunRequest / AcceptanceContract / Trace）
          ├── direct ───────────────────────┐
          └── isolate → TaskEngine → Worktree ├── Agent.run（同步 ReAct）
                            → Runtime ───────┘       ├── LLMBackend / Prompt / Model-aware budget
                                                    ├── Context / Repo Map / History
                                                    ├── Planning / Recovery / Skills controls
                                                    └── ToolExecutor → Native/MCP Tools
                                                          ↓
                                               Observation / Repository Effect
                                                          ↓
                                              Completion Guard / RunResult
                                                          ↓
                                        Runner Independent Acceptance / Trace
                                                          ↓
                                         Worktree artifact / optional GitHub PR

EvaluationHarness → Production Runner → Graders/Artifacts/Report
Post-run Evolution → Accepted traces → Candidate → Paired Eval → PromotionGate
```

**不要混淆的所有权**：Runner ≠ Orchestrator；Agent FINISH ≠ Independent Acceptance；TaskEngine state ≠ API task state ≠ Chat Session ≠ Trace；Worktree ≠ 安全沙箱；Skill control ≠ MCP remote side-effect tool；模型本地 token estimate ≠ Provider 实际 usage。上述主张来自设计文档并已读取部分关键实现，细节留给对应专题。

## 5. 已确认的边界事实（非质量评价）

1. **工具集合不是恒定 13 个**：`entry/cli.py::_build_registry` 中可注册 1 Shell + 4 File + 3 Search + 1 Pytest + 4 Git = 13 个原生 Tool；`_build_run_registry` 使用 `allow_git_mutation=False`，普通 CLI run 为 11 个；自动 PR 入口的可执行工具集合还受到交付所有权限制。Planning/Skill control schema 与 MCP 动态 Tool 另计；后续应按入口/模式逐一统计，不能以“全场景 13 个工具”宣传。
2. **真实架构是共享 Runner + 单 loop**：`agent/runner.py` 的 `RunRequest` 和 `ExecutionRunner`；`agent/core.py::Agent.run` 内创建单次 Planning/Recovery/Skill runtime；`agent/orchestrate.py` 只服务 isolate async resources。
3. **Repo Map SQLite schema 已定位**：`context/repo_index.py::_create_schema` 至少有 `metadata(key,value)`、`files(path,...,content)`、`symbols(file_path,ordinal,...)`、`imports(source_file,ordinal,...)`、`symbol_references(source_file,referenced_symbol,occurrences)` 五张表；设置 WAL/foreign_keys，使用版本/根路径一致性检查。这仅确认结构，**尚未评判 schema、索引或存全文 content 的必要性**。
4. **Context 三类事实源**：canonical History、model-facing compacted view、Chat Session state、EventLog 必须分别审计，避免用压缩效果替代恢复正确性判断。
5. **Feature 开关与实际使用率是独立问题**：`config/schema.py` 的 AgentCfg 默认 planning/recovery off，skills disabled；Benchmark 的 variant 可以改变配置。研究不能把“支持功能”误当“运行中默认启用/确实触发”。
6. **设计材料中的明确未实现边界**：没有多 Agent、parallel/multi-tool calls、任意同步执行的强制中断、分布式 Session、完整 OTel、在线 RL/参数更新或自动 Candidate promotion；这些应视为待评估的能力取舍，不自动判为缺陷。
7. **证据边界**：`docs/design/07-Evaluation与Evolution.md` 和根 README 声称 Benchmark V1 R2 baseline 与 Full P2 都是 23/24，且 Full P2 成本较高；本轮未读取冻结原始评测文件，故只作为阶段 09 待复核线索，不能计算通用胜率。

## 7. 外部对标方法与记录模板

主要对比 **Pi Agent、Codex CLI、Claude Code**，专题补充 Aider、SWE-agent、OpenHands 和必要的 Eval Framework。比较顺序固定为「Forge 问题与源码事实 → 对照项目真实实现 → 设计动机/差异 → 是否真正构成缺陷 → 性能/可靠性验证方案 → 改造代价 → 面试解释」。对源码不可见的 Claude Code，仅使用官方公开资料，不虚构内部文件路径。对照项目固定 commit、链接具体文件/符号；区分官方源码、官方文档、论文、二手讨论。

```text

```
