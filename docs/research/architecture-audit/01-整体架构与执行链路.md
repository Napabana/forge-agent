## 0. 先说结论（适合面试与 Baseline 决策）

1. **整体结构合理，暂不重写核心 Loop**。四个入口共享 `ExecutionRunner`；`Agent.run` 是单同步 ReAct，`orchestrate_run` 在 isolate 分支管理 Git Worktree、TaskEngine、Local/Docker、MCP 与 bus；`ToolExecutor` 管副作用治理，Runner 后置 Acceptance。这种分层适合独立实习项目，也与 Pi/Codex 的“核心执行与界面分离”设计理念一致，但不是实现等价。
2. **最大差异是异步事件调度**。Pi 的 `runLoop` 是真正 `async`；Codex 在核心 Session/Turn 层维护异步输入、取消与事件。Forge 在 `async def orchestrate_run` 中**直接同步调用** `agent.run(...)`，直到返回前不会主动把控制权让回同一 asyncio loop；它把事件放入 asyncio.Queue 的 forwarder 因而无法保证运行中即时被调度。外层的同步 `on_event` 回调和基于日志的 API SSE 是另一条通道，不应被一并认定无实时输出。这是明确的结构性限制，若要提供真正的 AgentBus 运行时事件流，需要针对性测试/改造。
3. **另一项需要验收的组合边界**：isolate 的 Worktree 在 `orchestrate_run` 返回前 finalize；Runner 在收到结果后才执行隐藏 verifier。若 `discard` 或无差异的 `keep-if-changed` 导致 `artifact.path=None`，`_apply_independent_acceptance` 会直接报 `worktree is unavailable...`，即使 verifier 本身只需要检查原有只读文件，也不会运行。这种语义在历史文档中被有意记录，但**对即将接入外部 Benchmark 的验收组合是否合适**必须提前决策。
4. **状态所有权相对明确**：`ApiTaskStore` 服务 HTTP 生命周期，`TaskEngine` 服务 isolate 工作树任务，`ChatSessionStore` 服务会话恢复，`EventLog` 服务审计，`RunResult` 另有 Agent/Acceptance/Delivery 三层状态。注意 `is_success()` 只表示 Agent 的 `SUCCESS`，不能在评测中直接等价于最终任务成功。
5. **建议的改进是有限的**：保留同步单 Loop 和独立 Runner；优先对隔离验收的工作区可用性建立回归，再针对 AgentBus 事件延迟做测试。没有证据支持现在进行全异步重构、增加 Subagent 或重做四入口。

本报告给的分数是**源码审查时的暂定工程评议分**，不是 Benchmark 结果；只用于定位下一轮验证和面试薄弱环节。

## 2. 当前真实执行拓扑（谁调用谁）

```text
CLI.run()                   ChatSession.run_round()        API create_task()           GitHub run_on_issue()
    │                               │                            │                          │
    │                              shared History          ThreadPoolExecutor             issue branch
    │                              pending_round               ApiTaskStore                verifier
    └───────────────────────────────┴────────────────────────────┴──────────────────────────┘
                                        │
                                 ExecutionRunner.run
                   预处理 AcceptanceContract / entrypoint / config
                                        │
                          ┌─────────────┴─────────────────┐
                       direct                           isolate
                          │                                │
                   existing/new Agent             asyncio.run(orchestrate_run)
                   ToolExecutor                        │
                   optional direct MCP          TaskEngine.create/claim
                          │                       WorktreeSession.create
                          │                       Local/Docker runtime/preflight
                          │                       isolated MCP + workspace ToolExecutor
                          │                                │
                          └──────────────┬─────────────────┘
                                    Agent.run
                       sync model → one Action → tool/control
                                    │
                         Trace + Completion Guard
                                    │
                    direct returns │ isolate first finalize Worktree
                                   ↓
                             Runner Acceptance
                                    │
                      final Result + acceptance trace
                                    │
             CLI output / Chat checkpoint / API state / Issue delivery
                                    │
                     EvaluationHarness → Grader → Trial
```

**五个不同生命周期：**

| 生命周期 | 触发/结束 | 对象所有者 | 持久状态 | 禁止混淆 |
|---|---|---|---|---|
| Product Request | `RunRequest` → `RunResult` | `ExecutionRunner` | Trace 文件/Result | Runner ≠ Agent |
| Agent Run | `Agent.run` 的 step/terminal | `Agent` | History（Chat 可持久）、Trace | FINISH ≠ 外部验收 |
| Isolate Run | engine claim → worktree finalized | Orchestrator + TaskEngine | TaskEngine SQLite、Worktree artifact | worktree keep ≠ PR |
| Chat Session | 每轮 pending/checkpoint/restore | `ChatSession` + Store | `state.json` + rounds | Trace 不等于可恢复 Chat 状态 |
| API Job | queued/running/cancel/succeeded/failed | `ApiTaskStore` | `api_tasks` SQLite | API ID ≠ Forge TaskEngine ID |
| GitHub Delivery | independent acceptance 后 commit/push/PR | `entry/github_issue.py` | branch/PR + delivery trace | Agent 不拥有自动 PR 提交权 |
| Eval Trial | materialize → Runner → grader | `EvaluationHarness` | suite/trial/patch/final state | Outcome/Process ≠ Agent SUCCESS |

### 2.1 `ExecutionRunner.run` 的两个分支：源码事实

**direct（`agent/runner.py::run`）**：

1. 按请求创建/复用 `ToolExecutor` 和 `Agent`；`_ensure_direct_mcp` 创建可跨 Chat/direct run 复用的 manager。
2. `RunRequest.history` 非空时，首个模型请求前由 `_prepare_shared_history_boundary` 对齐下一轮 History/Compaction 生命周期；`Agent.run` 中后续 step 依旧调用 `_prepare_next_turn`。
3. `EventLog` 可由 CLI/Chat 外部传入，否则 Runner 自建；支持 observer。
4. 主循环返回后直接对当前 repo 执行 acceptance，记录 `acceptance` 与 `run_terminated`。调用异常记录 `run_exception` 后继续抛出，并在 finally 关闭所拥有的 log。

**isolate（`agent/runner.py::run` → `agent/orchestrate.py::orchestrate_run`）**：

1. 禁止 shared History，必须有 `registry_builder`。
2. `asyncio.run` 进入 Orchestrator；创建/原子认领 TaskEngine Task，创建 EventLog、Worktree，按标志配置 LocalRuntime/DockerRuntime。
3. 容器模式在模型调用前 preflight；MCP manager 为本 run 创建、关闭；构造 bound registry/permission/executor。
4. 同步执行 `agent.run(task_in_wt, log)`；在 `finally` 中关闭 MCP manager 和 Runtime；检查/保留/删除 Worktree，并在 Engine 中 complete/fail；关闭 log/bus。
5. 返回 Runner 后，Runner 对 `result.worktree` 执行 hidden Acceptance，并重新打开 Trace 追加结果。

**审计含义**：两个分支共享核心 Agent、工具约束与结果模型，**但运行时资源所有权、共享 History、Acceptance 时间点不相同**。面试时不可回答“四入口全部先进入 Worktree”。

### 2.2 四入口差异矩阵

| 特性 | CLI `run` | Chat | HTTP API | GitHub Issue |
|---|---|---|---|---|
| 路径 | direct / isolate | direct | isolate | direct（独立 issue branch） |
| 共享 History | 单 run 默认否 | 是 | 否 | 否 |
| Session Store | 无 | `state.json` 原子持久化 | `ApiTaskStore` | 无 |
| Tool registry | `_build_run_registry`，默认不允许 Git add/commit | entry 注册工具，需追 Chat 的动态 set | isolate `_build_registry` | 自动 PR 模式移除 add/commit |
| Worktree | 只在 isolate | 否 | 默认有 | 不使用 isolate Worktree |
| Docker | optional `--sandbox` | 入口模式具体支持需按配置核查 | optional sandbox flag | 当前该入口未走 Docker 组合 |
| 独立验收 | 可配置 contract | 可配置 Runner，但普通交互不自动配置 hidden verifier | 此入口默认未提供 hidden verifier | 自动 PR 强制 verifier |
| 取消 | 中断/可配置 | 同步安全边界 | Thread Event cooperative cancel | 入口没有独立强制中止机制 |
| Trace 与反馈 | 终端 renderer、JSONL | 每轮 JSONL + Session | JSONL、HTTP/SSE | JSONL + delivery |
| 最终状态语义 | Agent status | round status + Session | API job status 与 isolate Agent status | Agent + Acceptance + Delivery |

**证据**：`entry/cli.py::_build_run_registry` 11 个原生工具；`entry/github_issue.py::run_on_issue` 先用 `_build_registry` 后按 `create_pr` 选择删除 `git_add/git_commit`；API 则构造 isolate `registry_builder=_build_registry`。这意味着“各入口的 Tool 集合一致”本身不成立，**是否应该一致是产品与评测协议选择，不是机械缺陷**。阶段 03 应固定准确的每入口工具集合。

### 2.3 命名相似但不同的对象

| 名称 | 源文件/owner | 真正负责 |
|---|---|---|
| `agent.task.Task` | `agent/task.py` / Agent | 模型执行的目标、require_changes/tests、max_steps |
| `task.engine.Task` | `task/engine.py` / Engine | 数据库中的可领取/阻塞/完成任务及 worktree |
| `ApiTask` | `entry/api_store.py` / HTTP API | API 请求队列、启动、取消、结果与日志引用 |
| `ChatSessionState` | `agent/session.py` + Store | 跨 round 完整恢复状态 |
| `EventLog` | `agent/event_log.py` | append-only 审计，不执行 replay |
| `RunResult` | `agent/task.py` | Agent/Acceptance/Delivery 三种状态的汇总 |
| `tools.runtime.RunResult` | `tools/runtime.py` | 单次子进程 exit/stdout/stderr，与 Agent RunResult 无关 |

这种分离可以保持职责明确，但 API/Engine/Runner 状态需要提供**明确的结果组合口径**，不能用一个 `success=True` 代替三层事实。

## 3. 成熟 Coding Agent 横向对照（版本固定）

### 3.1 Pi Agent：核心 Agent、AgentSession、执行模式分离

直接读取官方仓库固定 commit：

- [`packages/agent/src/agent-loop.ts`](https://github.com/earendil-works/pi/blob/b729499585bd7dacf6e9bc52994c6f157e35f9c9/packages/agent/src/agent-loop.ts)：公开的 `agentLoop`、`agentLoopContinue`、`runLoop` 实现；`runLoop` 是异步控制循环，具有 `prepareNextTurn`、`prepareRequest`、模型流、工具结果、steering/followUp 队列和 `finishTurn`。
- [`packages/agent/src/agent.ts`](https://github.com/earendil-works/pi/blob/b729499585bd7dacf6e9bc52994c6f157e35f9c9/packages/agent/src/agent.ts)：`Agent` 是独立可复用核心；消息/工具/模型/状态与 AbortSignal 抽象在 core 层。
- [`packages/coding-agent/src/core/agent-session.ts`](https://github.com/earendil-works/pi/blob/b729499585bd7dacf6e9bc52994c6f157e35f9c9/packages/coding-agent/src/core/agent-session.ts)：`AgentSession` 负责事件订阅、SessionManager、context compaction、retry、扩展和工作目录；源码说明其被 interactive/print/rpc 模式共享。
- [`packages/coding-agent/src/modes/print-mode.ts`](https://github.com/earendil-works/pi/blob/b729499585bd7dacf6e9bc52994c6f157e35f9c9/packages/coding-agent/src/modes/print-mode.ts)：print/json 模式复用同一 Session/Agent，负责输出/进程信号和 session disposal。

**与 Forge 对应**：Forge 的 `Agent.run` + `ExecutionRunner` + `ChatSession` 在职责上相近，但 Forge 的 Agent 本体承担更多 Planning/Recovery/工具控制的策略状态；Pi 的异步 `AgentSession` 明确承接事件/compaction/用户 steer 与跨模式会话管理。不要简单把 Pi 的 `AgentSession` 等同于 Forge 的 `ExecutionRunner`：Pi Session 除执行请求外还管理持久会话和交互功能。

**取舍**：Pi 的细粒度事件与动态输入更适合交互式长期任务；Forge 的同步顺序 Loop + 外层组合适合 deterministic failure harness。需求不同，不能根据 async/sync 单点判断好坏。

### 3.2 Codex CLI：核心 Session/Turn 与 UI 协议分层

直接读取固定 commit：

- [`codex-rs/core/src/session/mod.rs`](https://github.com/openai/codex/blob/1f1f6ebb6c156d5ab1d4745155f340b897b24f02/codex-rs/core/src/session/mod.rs)：core Session，拥有配置、活动 turn、event/submission 和资源状态。
- [`codex-rs/core/src/session/turn.rs`](https://github.com/openai/codex/blob/1f1f6ebb6c156d5ab1d4745155f340b897b24f02/codex-rs/core/src/session/turn.rs)：`run_turn` 异步模型-工具循环，记录输入、使用模型 client session、处理 hook、compaction、可追加用户输入和取消；比简单 ReAct 执行更多控制协议。
- [`codex-rs/core/src/state/turn.rs`](https://github.com/openai/codex/blob/1f1f6ebb6c156d5ab1d4745155f340b897b24f02/codex-rs/core/src/state/turn.rs)：`ActiveTurn`、`RunningTask`、`TurnState`，保存取消 token、批准请求/待输入、token usage 等 turn 内状态。
- [`codex-rs/docs/protocol_v1.md`](https://github.com/openai/codex/blob/1f1f6ebb6c156d5ab1d4745155f340b897b24f02/codex-rs/docs/protocol_v1.md)：解释 UI→Codex 提交队列 / Codex→UI 事件队列以及 Model/Session/Task/Turn 的区分。**注意该文件明确自述规范可能与当前代码不完全一致**；故仅作术语背景，细节仍依据上述源码。

**与 Forge 对应**：Codex 的 UI protocol 与 core 在工程层次上分离更清晰，可自然服务多 UI 和运行中用户交互；Forge 通过 Python 直接调用 `ExecutionRunner.run`，没有独立稳定的 host-core 消息协议。这是规模/需求选择，不是开展小模型 Benchmark 的必备条件。Forge 当前 `AgentBus` 只能算部分事件功能，不能描述为 Codex 式异步双向 Session Protocol。

### 3.3 Claude Code：官方外部行为，而非内部源码

- [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)：描述 gather context → take action → verify 的迭代循环、工具执行和用户中断。
- [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)：`claude -p` 与 Agent SDK 可复用同类 agent loop/tools/context；存在 non-interactive 和交互模式的配置边界。
- [Manage sessions](https://code.claude.com/docs/en/sessions)：支持 `--continue`、`--resume`、fork/branch；文档说明恢复会话不会自动重新执行中断的工具调用，并描述持久化历史与恢复语义。
- [Extend Claude Code](https://code.claude.com/docs/en/features-overview)：扩展点与配置的官方说明。

**证据边界**：可以比较公开 API、产品语义与生命周期；**不得推断 Claude Code 内部必然有与 Forge 相同的 `ExecutionRunner`、TaskEngine、Python 风格 Hook 管线或隔离数据表。** 后续专题依然遵守这个限制。

## 4. 功能级横向比较矩阵（本阶段 12 项）

## 5. 重点风险：逐条按控制流而非猜测分析

### R01：Isolate 的 AgentBus 不是可保证的实时异步事件发布（高置信源码判断）

源码链：[`agent/orchestrate.py::_bus_forwarder`](https://github.com/Napabana/forge-agent/blob/3e3fc48814aa15604c8a3a8a4432563854f8b6c1/agent/orchestrate.py) 用 `asyncio.Queue` 读取事件并 `await bus.publish`，但 `orchestrate_run` 建立 forwarder 任务后，在同一 asyncio event loop 线程**直接执行** `result = agent.run(task_in_wt, log)`。由于 `Agent.run` 是同步 Python 调用，在其返回前通常没有 asyncio 调度点，`_observe` 虽然 `put_nowait` 入队，forwarder 任务不能并行获得 event loop CPU 调度。因此对应 AgentBus events 通常只能在 Agent 返回、进入后续 await/finalize 时批量发送。

**不能误判**：`on_event` 回调会在 EventLog append 时同步调用，CLI renderer 可能实时展示；API 的 SSE 通过独立 HTTP 服务读取 JSONL，也不等于依靠同一 AgentBus forwarder。这两个产品路径不必同时失效。

| 项目 | 判断 |
|---|---|
| 影响 | 面向 AgentBus 的中途观察者不能期待低延迟事件；若同一 loop 中还承担 cancel/control，阻塞影响会放大 |
| 定位 | `agent/orchestrate.py` 的 `_observe`、`agent.run`、`_bus_forwarder` |
| 是否 P0 | **否**：当前 SFT/GRPO baseline 不要求 AgentBus 秒级推送 |
| 暂定优先级 | P2；如未来明确有 live bus 订阅或 async host 需求，升 P1 |
| 最小验证 | 用 FakeAgent 同步 sleep、EventLog 写进度、订阅 AgentBus，记录事件时间是否在 FakeAgent 返回后；与直接 `on_event` 收到时间对照 |
| 可选改进 | `await asyncio.to_thread(agent.run, task_in_wt, log)`，但需**先处理线程安全、callbacks、EventLog/SQLite 连接、取消、ContextVar 传播**，不能只改一行 |
| 成本估计 | 测试 S（0.5–1 人日）；最小异步桥接 M（2–4 人日）；全面 async core L（不推荐） |

### R02：Worktree 先 finalize、后 Runner hidden acceptance（明确的设计契约；对 Benchmark 有条件风险）

源码链：[Orchestrator finalization](https://github.com/Napabana/forge-agent/blob/3e3fc48814aa15604c8a3a8a4432563854f8b6c1/agent/orchestrate.py) 在返回前执行 `_finalize_worktree`，并给 `RunResult.worktree` 写入 artifact；[Runner acceptance](https://github.com/Napabana/forge-agent/blob/3e3fc48814aa15604c8a3a8a4432563854f8b6c1/agent/runner.py) 则在 `orchestrate_run` 返回以后根据 `result.worktree.path` 选定 workspace。若工作树被删除，`path=None`，`_apply_independent_acceptance` 会直接失败，不调用隐藏 verifier。历史 [2026-09-15 设计记录](https://github.com/Napabana/forge-agent/blob/fd700bdf48ace5f03bb9feab49d72f7c12e5ddcb/docs/changes/2026-09-15/Runner%E7%8B%AC%E7%AB%8B%E9%AA%8C%E6%94%B6%E9%97%AD%E7%8E%AF.md) 已明确规定 discard 失败，**不能把设计上明确写过的行为称为意外 bug**。

**为什么值得重新讨论**：未来一些外部 Benchmark trial 可能希望“Agent 可以写入临时 workspace → grader 验证 → 保存 patch/metrics → 丢弃 trial workspace”。如果 `discard` 在隐藏 grader 之前执行，该协议无法得到结果。对于 `require_changes=False` 的只读任务，即使 `keep-if-changed` 自动删除无改动 worktree，隐藏 verifier 仍可能需要读取文件，这也会失败。

| 项目 | 判断 |
|---|---|
| 确认性质 | 代码上的确定性先后顺序 + 历史明确契约 |
| 影响 | 使用 isolate + hidden verifier + 先 discard，或无变更保留策略，可能出现本可验收但找不到工作区 |
| 现有 P2 Evaluation | `evals/coding_agent/runner.py::_run_trial` 当前通过独立 materialization 并使用普通 `RunRequest(task, acceptance, entrypoint='eval')`，默认 direct；所以**不把这一点当成已证明会污染现有 Benchmark V1 的缺陷** |
| 暂定优先级 | **条件 P1**：若未来 Repo2RLEnv/GRPO evaluator 采用 isolate + hidden grader + discard，进入训练前必须明确/修复 |
| 最小验证 | FakeAgent 成功且无改动、isolate=true、`AcceptanceContract(verifier=...)`、两种 result policy；断言 verifier 是否真的运行和最终 acceptance |
| 建议设计 | 把 hidden acceptance 安排在 **Agent 完成且工作区仍可访问**的生命周期点，再执行“保留或删除”策略；继续保证 verifier 不进入 Agent History，并在 Trace 记录 terminal+acceptance+artifact 顺序 |
| 成本估计 | 最小契约测试 S；Runner/Orchestrator ownership 重排 M（2–4 人日）；不建议顺带全面重构 Runner |

### R03：TaskEngine 与 Acceptance/ApiTaskStore 的“成功”含义必须分开（文档/指标风险）

- `TaskEngine.complete_task` 在 isolate Orchestrator 内依据 `result.is_success()` 完成，**早于** Runner 的独立 acceptance。
- `RunResult.is_success()` 在 `agent/task.py` 仅判断 Agent status；若 `acceptance_status='failed'`，`RunResult.status` 仍可为 SUCCESS。
- `entry/api.py::run_agent_task` 用 Agent status 决定 API `STATUS_SUCCEEDED`，该入口目前默认不提供 hidden verifier。GitHub PR 的 `deliver_pull_request` 则另外要求 `acceptance_status == 'passed'`；`EvaluationHarness` 又要求 run status、acceptance 和 required graders。

**结论**：这是不同状态域的有意设计，**不是“TaskEngine.complete_task 肯定有 bug”**。但以后只报告 TaskEngine completed 或 API succeeded 可能误导最终验收结果，尤其外部 Benchmark 适配器若误用 `run_result.is_success()` 单条件。

**建议**：写一张全入口 result mapping contract，并在 eval 入口做一个状态真值表测试（agent SUCCESS × acceptance passed/failed/skipped × grader pass/fail），确保定义唯一。

- 暂定优先级：P1（**口径与 adapter 测试**，不一定修改源码）。
- 成本：S（0.5–1 人日）。

### R04：Runner `asyncio.run` 的 async caller 兼容（已知边界）

`ExecutionRunner.run` isolate 分支直接调用 `asyncio.run(orchestrate_run(...))`；在同一线程已有运行中的 event loop 里调用会产生 `RuntimeError`。当前 API 把请求放进 `ThreadPoolExecutor` 工作线程，CLI 是同步调用，所以当前产品路径合理；但未来如果把 Forge 作为异步 RL env 或 SDK 在 async loop 内直接调用，就不应从 coroutine 中使用这个同步入口。

建议先按训练框架实际调用模型选择：worker thread 包装 / 提供显式 `run_async` / 训练环境同步 API；**先定义稳定 contract，后决定是否开发**。优先级 P2（若 RL env async 强依赖则 P1）；适配 S～M。

### R05：入口配置、原生工具与生命周期差异（公平性风险）

- `entry/cli.py::_build_run_registry` 禁止 Git add/commit，`_build_registry` 可全部注册；API isolate 由 `_build_registry` 构造；Issue 自动交付再次移除 mutation 工具。
- `config/schema.py` 有 Planning/Recovery/Skills 默认关闭的配置，入口在构造 `AgentConfig` 时各自显式赋值。
- `ExecutionRunner.run` 可能推断 `entrypoint`（根据 issue_url/cancel_event/history），也支持显式传入。

**建议**：评测时不使用 CLI/Chat/API 的默认设置作为不可见变量；由 `EvaluationSuite` 固化 `RunRequest`、Tool manifest、config hash、runtime、worktree policy、model output reserve 和 acceptance，避免多入口差异影响 SFT/GRPO 的 attribution。阶段 09 验证是否已有这些 manifest 字段以及实际覆盖程度。优先级 P1（实验协议）；成本 S。

### R06：API queue limit 可能存在并发 admission 竞争（未复现推断）

`entry/api.py::create_task` 先 `store.count_active()` 判断队列限额，再 `store.create_task()`，两者分别执行。并发 HTTP 请求下可能在同一阈值前同时通过，超出逻辑 queue_limit；`tests/test_api.py` 已有顺序请求 429 测试，**本轮尚未看到并发 admission 测试**。这是审阅推断，需要并发测试才能确认，不作为训练阻塞。优先级 P2；成本 S。

### R07：资源持有者和清理的可核查程度

- Runner 持有 direct MCP manager；`close()` 显式关闭。Chat 持有 Runner 并跨轮复用。
- Orchestrator 的 per-run MCP manager 和 Local/Docker runtime 在 `finally` 内清理；Worktree finalize 和 EventLog close 分别受异常路径影响。
- `tests/test_orchestrate.py` 已写入 fake Docker cleanup、真实 worktree retain、异常清理、EventLog 顺序测试；但本轮没有执行这些测试，尚未核对所有错误注入组合的资源泄漏行为。
- `entry/api.py` 维护 `cancel_events` dict，并以 `_run_task_and_cleanup` 清理；线程池 shutdown 为 `wait=False,cancel_futures=True`。这适合轻量服务，但与“分布式可靠后台任务”不同。

建议阶段 07 使用 failure-injection matrix 覆盖 preflight、Agent crash、MCP close、Worktree finalize、Trace append failure、API cancel。优先级 P2；成本 M（视覆盖缺口）。

## 8. Benchmark/GRPO 是否可以开始？

**阶段 01 的局部判定：可以继续进行 Evaluation Harness 的静态核查和可控 fixture 测试；暂不能凭此宣告整个 baseline 已可信。**

当前 `evals/coding_agent/runner.py::_run_trial` 的主要路径是 **materialize 一份独立 repo → Production Runner direct → hidden verifier/graders → trial artifact**。因此本阶段发现的 isolate worktree finalize 顺序问题，在**现有 direct Trial** 下并非已证实阻塞项。

未来若把 Forge 接入 Repo2RLEnv / GRPO，必须在任务配置里显式冻结并留档：
- `mode`: direct / isolate；是否 sandbox 和结果策略。
- `model/provider/config`: 模型 ID、版本/量化、sampling、max_output、token budget、max_steps、retry。
- `tools`: Tool manifest、权限/只读约束、MCP、Planning/Recovery/Skills 的开启情况。
- `grader`: hidden tests、reward 函数/版本、验收与过程指标区分、失败/超时处理。
- `artifact`: 每试次 commit、初始快照、最终 diff、Trace、上下文指纹。
- `attribution`: 同一 Harness 固定后先比较 teacher/student 模型，再固定 student 比较 SFT、GRPO；不要同时改 Harness 与模型权重。

实现前先让两个实验组合成立：① direct+frozen acceptance+single model；② 若要 isolate，先验证 hidden grader 可在清理前访问 trial repo。

## 9. 面试复习：用源码回答，而不是背名词

**Q1：Forge 和 Pi/Codex 的整体架构差异？**  
答：Forge 是四入口共享 `ExecutionRunner → Agent.run → ToolExecutor` 的 Python Coding Agent；isolate 单独由 `orchestrate_run` 管 Worktree/Runtime。Pi 把 agent core、异步 Agent loop 和 AgentSession 分开并复用到 interactive/print/rpc；Codex 把异步 Session/Turn core 与客户端消息/事件协议分开。Forge 为简化状态机和测试保留同步 loop，代价是更弱的异步事件与运行时交互能力。

**Q2：为什么 Runner 和 Orchestrator 同时存在？**  
答：Runner 属于所有入口共用的产品执行契约，控制 direct/isolate、Trace 和独立验收；Orchestrator 只在 isolate 模式管理 TaskEngine、Worktree、Docker/MCP 和最终清理，两者 owner 不同。不是两套 Agent loop。

**Q3：为什么不用 `async def Agent.run`？**  
答：当初明确以顺序可测试、低实现成本为优先；Provider、Tool、状态转换都按 step 顺序发生。现在确认同步 Agent 在 async Orchestrator 内运行可能阻塞 AgentBus forwarder。如果未来需要实时事件或 async RL env，会先做有界桥接与测试，再决定是否更大改造，不能宣称同步天然更快或更可靠。

**Q4：API 有两套 Task ID 是不是重复设计？**  
答：HTTP ApiTask ID 记录排队、取消和 HTTP 请求状态；TaskEngine ID 记录 isolate Agent 工作区任务的 claim/complete/fail。它们是两个状态域，通过 `forge_task_id` 关联；不能把它们当同一个数据库实体。

**Q5：Agent 返回 SUCCESS 是否说明任务完成？**  
答：不是。Agent 的 SUCCESS 来自内部 Completion Guard；Runner 可额外运行模型不可见的 hidden verifier，独立记录 `acceptance_status`；GitHub delivery 还要检查这两层状态后执行 commit/push/PR。训练 reward 与任务成功率不能只读取 `RunResult.is_success()`。

**Q6：为什么不直接照搬 Codex 的双向 Session Protocol？**  
答：Forge 目前只有 CLI/Chat/API/Issue、单一 Agent，且重点是受控任务执行和评测；直接 Python 调用足够明确。若后续出现多 UI 实时控制/恢复需求，再抽出稳定的 submission/event contract；提前实现会增加测试/兼容成本而未证明收益。

**Q7：现阶段最值得改哪一处？**  
答：不是新增工具，也不是重写 Agent Loop，而是先把训练环境依赖的执行契约测清楚：是否 direct/isolate、hidden verifier 在清理前能否运行、什么叫任务成功、不同实验工具/预算是否相同。AgentBus 的实时性是另一个可通过定向测试验证的工程改进点。
